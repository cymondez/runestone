# Runestone DNS

[English](DNS.md) | [繁體中文](DNS.zh-TW.md) | 日本語

このドキュメントは、Runestone の DNS 機能が何をするのか、マシンの何を変更するのか、そしてどう元に戻すのかを説明します。**通常の機能説明より長いのは、この機能がグローバルな状態を変更するためです**。Docker daemon の設定を編集し、Docker を再起動します。有効にする前に、それが何を意味するのかを正確に知っておいてください。

短い版だけ知りたい場合: プロジェクトのドメインが**コンテナの内側でも**正しく解決されるようになります。その代償として、このマシン上のすべてのコンテナが DNS を Runestone のコンテナに問い合わせるようになります。既定では無効で、`runestone dns disable` で取り除けます。

## 解決する問題

Runestone は、プロジェクトに本物のドメインと本物の証明書を与えます — `localhost:3000` ではなく `app.local.example.net` です。ブラウザからはこれで動きます。Runestone の証明書と Traefik のルーティングが面倒を見てくれるからです。

しかし**コンテナの内側**からは動きません。Runestone のドメインは公開 DNS 上では `127.0.0.1` に解決され、コンテナの中では `127.0.0.1` はそのコンテナ自身です。つまり `https://api.local.example.net` に接続しようとするバックエンドのコンテナは、自分自身のループバックに接続して接続エラーになります — あるいはもっと悪いことに、たまたまそこで待ち受けている無関係なサービスに届きます。

そしてこの失敗は静かです。「このドメインは間違った場所に解決されました」と報告するものは何もありません。接続エラーか、間違ったサービスからの間違った答えが返ってきて、あなたは自分のアプリケーションのバグを探しに行くことになります。

DNS 機能は、Runestone のドメインを知っているリゾルバをコンテナに与えることでこれを解決します。有効にすると、`api.local.example.net` を問い合わせたコンテナはホストマシンのアドレスを受け取り、Traefik に届き、ブラウザとまったく同じようにルーティングされます。

## 有効にするとマシンに何が起きるか

以下のすべては、CLI が実際に何かを変更する前に、あなたの実際の値を埋めた形でもう一度開示されます。始める前に読めるよう、ここにも書いておきます。

### 1. Docker daemon の設定を編集します

Runestone は次のファイルの `dns` 配列に項目を 1 つ追加します。

| 環境 | ファイル |
| --- | --- |
| Docker Desktop (Windows、macOS) | `~/.docker/daemon.json` |
| ネイティブ Linux Docker Engine | `/etc/docker/daemon.json` (`sudo` が必要) |

その項目は、コンテナがホストに到達するために使うアドレスです — Docker Desktop では通常 `192.168.65.254` です。配列の**先頭**に追加されます。daemon はこれらを順番に問い合わせるので、Runestone が最初に問われる必要があるからです。

Runestone は自分が所有するバイトだけを編集します。既存の設定、その順序、インデントはそのまま残ります。

### 2. Docker の再起動が必要で、それはすべてのコンテナを停止します

Docker daemon がそのファイルを読むのは起動時だけです。Docker が再起動するまで、**その変更はまったく効果を持ちません** — これは意図的であり、Runestone がファイルの書き込みと再起動を分けている理由でもあります。

再起動は**このマシン上のすべてのコンテナ**を終了させます。Runestone とは何の関係もないコンテナも含めてです。データベース、キュー、動かしているものすべてです。restart policy が `always` または `unless-stopped` のコンテナは通常は自分で戻ってきますが、policy がないコンテナは戻りません。

始める前に何が動いているか確認してください。

```bash
docker ps
```

### 3. その後、すべてのコンテナの DNS が Runestone のコンテナを経由します

これは過小評価されやすい代償です。有効にすると、**このマシン上のすべてのコンテナからのすべての DNS クエリ**が — Runestone のプロジェクトだけでなく — Runestone の `dns` コンテナに向かいます。

そのコンテナが停止していたり、再作成中だったり、イメージの取得を待っていたりすると、マシン全体のコンテナが何も解決できなくなる可能性があります。これを和らげる唯一の選択肢については[フォールバック設定](#11-フォールバック項目)を参照してください。

### 4. ホストの 53 番ポートが占有されます

`dns` コンテナは 53 番ポートを **TCP と UDP の両方で**公開します。マシン上の別の何かが既にそれを持っている場合、サービスは起動しません — そして Runestone は daemon の設定に触れる前にそれを伝えます。

### 5. `runestone stop` は意図的に DNS サービスを動かしたままにします

`runestone stop` は Runestone 環境を停止しますが、**`dns` コンテナは動かしたままにします**。これは見落としではありません。Docker daemon がそれを指しているため、停止するとこのマシン上のすべてのコンテナの名前解決が壊れます。

一緒に停止するには:

```bash
runestone stop --all
```

これは再び起動するまで DNS をマシン全体で無効にします。Runestone は実行前に警告します。

### 6. Runestone を削除する前に無効にしてください

DNS を有効にしたまま Runestone を削除すると、Docker daemon はもう存在しないコンテナを指したまま残されます。マシン上のすべてのコンテナが何も解決できなくなり、その理由を説明するものはマシン上のどこにもありません。

**Runestone を削除する前に必ず `runestone dns disable` を実行してください。** すでに手遅れの場合は[手動で項目を削除する](#手動で項目を削除する)を参照してください。

### 7. 無効化は Runestone が追加したものだけを削除します

Runestone は自分が挿入した項目を正確に記録しています。`runestone dns disable` はそれらだけを削除し、それ以外は何も触りません — 他のすべての項目は値も位置もそのまま残ります。

どれが自分のものか確実に判断できない場合 — ファイルが手で編集された、あるいは同じアドレスが複数回現れる — **何も削除せず、そう伝えます**。推測して、あなたが依存しているリゾルバを削除することはしません。その場合は明示的に指定できます。

```bash
runestone dns disable --assume-entry 192.168.65.254
```

### 8. DNS の Web UI は既定で認証がありません

Runestone は `https://dns.<あなたのドメイン>` に、自分の dnsmasq ルールを編集するための小さな Web UI を用意します。**`DNS_UI_USER` と `DNS_UI_PASS` が未設定の場合、認証はまったくありません** — HTTPS でこのマシンに到達できる人は誰でも DNS ルールを変更できます。

両方を設定するか、UI を無効にしてください。

```dotenv
DNS_UI_ENABLE=false
```

### 10. Runestone のドメイン以外はすべて上流へ転送されます

`dns` コンテナは Runestone のドメインを自分で答え、それ以外はすべて上流のリゾルバへ転送します。つまり、**このマシン上のすべてのコンテナからの通常のインターネット問い合わせは、ここで設定したサーバーを通ります。**

このリストが空になることはありません — 空だと、コンテナはインターネットの名前解決を完全に失います。Runestone はまず Docker daemon の設定を、次にホスト自身のリゾルバを見てリストを組み立て、他に何も判明しなかった場合にのみ公開の `1.1.1.1` にフォールバックします。どちらが起きたか、そして各値がどこから来たかを伝えます。

複数の値は**優先順位ではなくプール**です。dnsmasq は最も早く応答したものを優先します。順番に試したい場合は、Runestone が決して上書きしない `dns/custom.conf` に `strict-order` を追加してください。

### 11. フォールバック項目

既定では無効です。`DNS_DAEMON_FALLBACK` を設定すると、Runestone は自分の項目のすぐ後ろに**2 つ目**の項目を追加し、daemon が問い合わせられる先をもう 1 つ用意します。

どちらの方向も重要です。

| | フォールバック無効 (既定) | フォールバック有効 |
| --- | --- | --- |
| DNS サービスが動作中 | 違いなし | 違いなし |
| DNS サービスが停止中 | 問い合わせは即座にはっきりと失敗し、原因が明白 | 通常のインターネット名は解決され続ける。マシン上のすべてのコンテナで |
| サービス停止中に Runestone のドメイン | 失敗する | **`127.0.0.1` に解決される** — 最初の問題が戻ってくる |

つまり有効にすると、無関係なプロジェクトの回復力が得られ、DNS 障害を明白にしてくれる「大きな失敗」を失います。Runestone の助言:

- **このマシンで Runestone と無関係なプロジェクトのコンテナも動かしている** → 通常は有効にするのが適切です。Runestone のコンテナが止まったせいで、それらのプロジェクトがインターネット DNS を失うべきではありません。
- **主に Runestone の開発に使うマシンで、DNS の不調をすぐ気づきたい** → 通常は無効のままが適切です。
- **迷う場合** → 無効のままにしてください。後から有効にする費用は、daemon への書き込み 1 回と Docker の再起動 1 回だけです。

## 有効にする

`runestone setup` は DNS が必要かどうかを尋ね、回答を記録します。**セットアップは有効化しません** — Docker daemon の設定には決して触れません。有効化は独立したコマンドです。必要な 2 つの確認が、そのために実行したコマンドに属するようにするためです。

何も変更せずに、何が変わるかだけを確認する:

```bash
runestone dns enable --dry-run
```

実際の値を埋めた完全な開示と、`dns` 配列の正確な前後比較を表示し、何も書かずに終了します。

有効にする:

```bash
runestone dns enable
```

2 回尋ねられますが、この 2 つの質問は別のものです。1 つ目は daemon 設定を編集することへの同意。2 つ目は Docker を再起動することへの同意で、こちらがコンテナを止める部分です。1 つ目に答えても 2 つ目を約束したことにはなりません。

グローバルなものを書き込む前に、Docker に到達できることを確認し、コンテナが使うべきアドレスを求め、DNS サービスを起動し、**そのサービスに実際の問い合わせを行って**正しく答えることを確認します。失敗しうるものはすべて、マシンのグローバルな DNS が触られる前に失敗します。

### 今書き込んで、後で再起動する

```bash
runestone dns enable --no-restart
```

daemon 設定を書き込んで停止します。あなた自身が都合のよいときに Docker を再起動するまで、何も有効になりません。`runestone dns status` は変更が書き込まれて待機中であることを伝え続けます。

## 現在有効な設定を確認する

```bash
runestone dns status
```

読み取るだけで、何も変更しません。daemon 設定のパス、Runestone の各項目が配列の実際にどこにあるか、コンテナが解決するアドレス、上流リストと各値の出どころ、フォールバックが有効かどうか、Web UI に認証があるかどうかを報告します。

`runestone doctor` も、DNS が有効なときは DNS について報告します。Runestone の項目がまだ先頭にあるか、サービスが動いているか、アドレスがまだ一致しているか、ドメインのマッピングが最新かどうかです。**`doctor` は報告するだけです** — daemon 設定を編集することはありません。どの項目が Runestone のものかを診断コマンドが推測してよいものではないからです。

## 無効にする

```bash
runestone dns disable
```

Runestone が自分のものとして記録した項目を削除し、削除が有効になるよう Docker を再起動し、`dns` コンテナを停止して削除します。あなた自身の `dns/custom.conf` は残ります — それはあなたのものです。

先に何をするか確認するには:

```bash
runestone dns disable --dry-run
```

`runestone down` も環境を撤去する前に自動的に DNS を無効化し、それが失敗した場合は**何も削除せずに中止します** — daemon がまだ指している状態で `dns` コンテナを削除することは、まさにこの機能が防ぐために存在する失敗だからです。

## 手動で項目を削除する

Runestone がもうない場合や、所有権の記録が失われた場合は、自分で項目を削除できます。魔法は何もありません — JSON 配列の中の 1 つの文字列です。

1. daemon 設定ファイルを開きます。
   - Docker Desktop: `~/.docker/daemon.json`
   - ネイティブ Linux: `/etc/docker/daemon.json` (`sudo` が必要)

2. `dns` 配列を見つけます。だいたいこのような形です。

   ```json
   {
     "dns": ["192.168.65.254", "1.1.1.1"],
     "experimental": false
   }
   ```

3. Runestone が追加したアドレスを削除します — Docker Desktop では通常 `192.168.65.254`、ネイティブ Linux では `172.17.0.1` のような docker0 ゲートウェイです。**他の項目には手を触れないでください。** 削除した結果 `dns` 配列が空になる場合は、`dns` キーごと削除して構いません。

4. Docker がファイルを読み直すよう再起動します。

   ```bash
   docker desktop restart
   ```

   ネイティブ Linux では:

   ```bash
   sudo systemctl restart docker
   ```

   どちらも使えない場合は、普段の方法で Docker を再起動してください。**この編集は再起動後にのみ有効になる**ので、それまでは何も変わっていません。

5. 新しいコンテナがもうそれを指していないことを確認します。

   ```bash
   docker run --rm alpine cat /etc/resolv.conf
   ```

## うまくいかないとき

### DNS サービスが起動しない: 53 番ポートが使用中

マシン上の別の何かが 53 番ポートを持っています。Runestone はこれを `netstat` を読むのではなく、実際にサービスを起動してみることで判断します — ポートは空いて見えても使えないことがあり、使用中に見えても動くことがあり、しかも TCP と UDP で答えが違うこともあるからです。

**Windows ではこれはたいてい Internet Connection Sharing サービス**で、WSL2 がそれを有効にします。これは `0.0.0.0:53/udp` を保持します。Runestone はそれと共存できる形式で 53 番ポートを公開するので通常は問題ありませんが、`DNS_BIND_IP` を自分で設定している場合は空にしてみてください。

その他のよくある保持者: Linux の `systemd-resolved` (`127.0.0.53` を保持)、Pi-hole、dnsmasq、あるいは別のローカル DNS サーバー。

何が保持しているかを見るには:

```bash
netstat -ano | findstr :53
```

Linux では:

```bash
sudo ss -ulpn 'sport = :53'
```

### コンテナが何も解決できない

まず DNS サービスが動いているか確認します。

```bash
runestone dns status
```

動いていなければ起動します。

```bash
runestone up
```

起動できず、今すぐマシンを使える状態にする必要がある場合は、DNS を無効にしてください。

```bash
runestone dns disable
```

同じことが再び起きないよう、[フォールバック設定](#11-フォールバック項目)も検討してください。

### Runestone の項目が先頭ではなくなった

別の何かが自分の項目を Runestone より前に追加しました。daemon は順番に問い合わせるため、Runestone が最初に問われなくなり、ドメインが解決されなくなる可能性があります。

`runestone dns status` と `runestone doctor` はどちらも実際の位置を報告します。既定では Runestone は**警告するだけで何も変更しません**。頼まれてもいないのに他人の設定を並べ替えるのは、その役目ではないからです。`runestone up` のたびに自分の項目を先頭へ戻させるには:

```dotenv
DNS_AUTO_REORDER=true
```

自分の項目だけを動かし、他人のものには決して触れず、そのために Docker を再起動することもありません — 変更は次に Docker を再起動したときに有効になります。

### daemon 設定は書き込まれたのに何も有効にならない

それは `--no-restart` の後、および再起動が完了しなかった実行の後に期待される状態です。`runestone dns status` がそう伝えます。Docker を再起動すれば有効になります。

### 再起動が失敗してマシンが妙な状態になった

再起動や検証が失敗したとき、Runestone は自分の変更を元に戻します。そして**修正したファイルを書いてから再起動します** — なので 2 回目の再起動も失敗したとしても、ディスク上のファイルは既に正しく、Docker は次回起動時にそれを読みます。

信用できないファイルが残ってしまった場合は、[手動で項目を削除](#手動で項目を削除する)してください。正確なパスはすべての失敗メッセージに表示されます。

## 設定

以下はすべて Runestone の `.env` にあります。

| 設定 | 既定 | 意味 |
| --- | --- | --- |
| `DNS_ENABLE` | `false` | DNS が有効かどうか。**`dns enable` / `dns disable` が管理します** — 手で設定しても何も有効化・無効化されず、Runestone の報告と現実がずれるだけです |
| `DNS_HOST_IP` | *(自動検出)* | コンテナが Runestone のドメインを解決するアドレス。Runestone が管理します |
| `DNS_BIND_IP` | *(自動検出)* | 53 番ポートがバインドするホストアドレス。空または `0.0.0.0` はすべてのインターフェース |
| `DNS_UPSTREAM` | *(自動検出)* | カンマ区切りの上流リゾルバ。空は検出、その後 `1.1.1.1` にフォールバック |
| `DNS_DAEMON_FALLBACK` | *(空)* | 2 つ目の daemon 項目。空は無効。[項目 11](#11-フォールバック項目) を参照 |
| `DNS_AUTO_REORDER` | `false` | `up` のたびに Runestone 自身の項目を先頭へ戻すかどうか |
| `DNS_CONTAINER_RESOLVER` | *(自動検出)* | DNS コンテナ自身が使うリゾルバ |
| `DNS_UI_ENABLE` | `true` | `https://dns.<あなたのドメイン>` を Web UI にルーティングするかどうか |
| `DNS_UI_USER` | *(空)* | Web UI のユーザー名。未設定は**認証なし** |
| `DNS_UI_PASS` | *(空)* | Web UI のパスワード。未設定は**認証なし** |

`.env` には `DNS_BIND_PREFIX` も現れます。これは Compose ファイルのために `DNS_BIND_IP` から導出されたものです。変更したい場合は `DNS_BIND_IP` を設定してください。

### 自分の dnsmasq ルール

Runestone ディレクトリ内の `dns/custom.conf` はあなたのものです。Runestone は一度だけ作成し、**決して上書きしません**。自分の `address=` や `server=` の行、あるいは上流を順番に試したい場合の `strict-order` に使ってください。

Runestone が生成するもう 2 つのファイル — `dnsmasq.conf` と `managed.conf` — はコンテナの内側にのみ存在し、起動のたびに再生成されます。触ることはできませんし、その必要もありません。各起動が生成するものが正しく、CLI が実行されたかどうかには一切依存しません。
