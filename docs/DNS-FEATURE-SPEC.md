# Runestone DNS Feature Project Specification

## 1. Status and authority

- Status: Proposed
- This document is the authoritative specification for the Runestone DNS feature.
- The DNS feature notes in `TODO` are background material only.
- Normative terms are defined by RFC 2119 and RFC 8174.

## 2. Goal and scope

The feature allows Docker containers to resolve Runestone-managed local domains to the host gateway, so requests can reach the Runestone reverse proxy instead of resolving to container-local loopback addresses.

### 2.1 In scope

- Windows, macOS, and Linux local Docker environments.
- `runestone setup` DNS toggle.
- `runestone dns enable`, `runestone dns disable`, and `runestone dns status`.
- A dedicated DNS service running dnsmasq and Webproc.
- Docker daemon `dns` ownership, reconciliation, rollback, and selective removal.
- DNS mappings generated from Runestone certificate files.
- Lifecycle integration with `up`, `stop`, `down`, and certificate changes.

### 2.2 Out of scope

- Changing the host operating system's DNS configuration.
- Adding, removing, or requiring user-selected fallback DNS entries in Docker daemon configuration.
- Remote Docker contexts.
- IPv6 host-gateway resolution.
- Linux rootless Docker environments that cannot publish privileged port 53.
- Webproc username/password authentication.

## 3. Terminology

| Term | Definition |
|---|---|
| `host.docker.internal` | Docker-provided hostname that resolves to the Docker host gateway. |
| Target IP | The IPv4 address obtained by resolving `host.docker.internal` from the Docker environment. |
| Owned DNS entry | A DNS array entry that Runestone inserted or moved and recorded in ownership state. |
| Managed mapping | A dnsmasq mapping generated by Runestone from a certificate domain. |
| Custom rules | User-authored dnsmasq rules stored independently of managed mappings. |
| DNS service | The independent Compose service that runs dnsmasq and Webproc. |

## 4. Architecture

The Compose project definition is governed by `DNS-RUN-001` through `DNS-RUN-008`; the following diagram is explanatory:

```text
Docker containers
      │
      │ DNS query
      ▼
Docker daemon dns[0] = Target IP
      │
      │ Target IP:53/tcp and Target IP:53/udp
      ▼
Runestone dns service
      ├─ dnsmasq :53
      └─ Webproc  :8080
             │
             ▼
      Traefik https://dns.<HOST_DOMAIN>
```

Docker daemon DNS configuration is stored in a platform-specific daemon JSON file and requires a daemon restart after modification. Docker documents `/etc/docker/daemon.json` for native Linux and `$HOME/.docker/daemon.json` for Docker Desktop.[Docker daemon configuration](https://docs.docker.com/engine/daemon/)[Docker Desktop settings](https://docs.docker.com/desktop/settings-and-maintenance/settings/)

## 5. Normative requirements

### 5.1 CLI and setup

### CLI-001 — The CLI MUST expose `runestone dns enable`, `runestone dns disable`, and `runestone dns status`.
### CLI-002 — Setup MUST provide a DNS enable/disable prompt and show the selected value in the review summary.
### CLI-003 — DNS MUST be disabled when `DNS_ENABLE` is absent.
### CLI-004 — Setup prompt descriptions MUST explain that enabling prepends the Target IP to Docker daemon DNS and restarts Docker.
### CLI-005 — Setup validation errors MUST be rendered in the same prompt description and MUST return to that prompt.
### CLI-006 — Cancelling or failing preflight MUST leave daemon configuration, service state, and ownership state unchanged.
### CLI-007 — `dns status` MUST report desired state, DNS service state, Target IP, daemon config path, ownership state, and UI URL without mutating state.
### CLI-008 — Enable and disable MUST request confirmation before restarting Docker daemon or Docker Desktop.
### CLI-009 — Successful commands MUST exit with code `0`; operational failures MUST exit non-zero.

### 5.2 DNS service and image

### RUN-001 — Compose MUST define DNS as an independent `dns` service.
### RUN-002 — The DNS service MUST use a dedicated Compose profile and MUST NOT start when DNS is disabled.
### RUN-003 — The DNS service MUST publish `Target IP:53` for both TCP and UDP.
### RUN-004 — Webproc port `8080` MUST NOT be published directly to the host.
### RUN-005 — The main Runestone service MUST NOT start dnsmasq.
### RUN-006 — The image MUST contain dnsmasq and a pinned Webproc binary.
### RUN-007 — The DNS service MUST expose Webproc internally at port `8080`.
### RUN-008 — The DNS service MUST bind port 53 only to Target IP and MUST NOT silently fall back to `0.0.0.0`.

### 5.3 Certificate mappings and UI

### MAP-001 — DNS service startup MUST scan `/ssl` for certificate files.
### MAP-002 — `rootCA.crt` and invalid domain filenames MUST be excluded.
### MAP-003 — Each valid certificate domain MUST generate a dnsmasq mapping to Target IP.
### MAP-004 — Each mapping MUST resolve both the certificate base domain and its subdomains.
### MAP-005 — Managed mappings MUST be regenerated whenever the DNS service starts.
### MAP-006 — Managed mappings MUST be stored separately from user-editable custom rules.
### UI-001 — The UI MUST be available at `https://dns.<HOST_DOMAIN>`.
### UI-002 — Traefik MUST route the UI to the internal `dns:8080` service.
### UI-003 — The UI MUST edit only the persistent custom rules file.
### UI-004 — Webproc MUST NOT edit or replace Runestone-managed mappings.
### UI-005 — The UI MUST use no authentication, and setup/help output MUST disclose that anyone able to reach the Runestone HTTPS route can edit custom rules.

dnsmasq supports domain-specific address mappings and upstream forwarding through its configuration file.[dnsmasq manual](https://thekelleys.org.uk/dnsmasq/docs/dnsmasq-man.html) Webproc provides a web UI for process status, logs, and configured files.[Webproc](https://github.com/jpillora/webproc)

### 5.4 Docker daemon ownership

### DMN-001 — Enable MUST resolve the IPv4 Target IP from the Docker environment before changing daemon configuration.
### DMN-002 — Enable MUST place Target IP at index `0` of the daemon `dns` array.
### DMN-003 — Enable MUST preserve every daemon key other than the required Runestone DNS change.
### DMN-004 — Existing DNS entries MUST retain their relative order.
### DMN-005 — Runestone MUST record daemon path, Docker context, Target IP, operation type, original index, file/key existence, and transaction phase.
### DMN-006 — If Target IP is absent, the operation MUST be recorded as `inserted`.
### DMN-007 — If Target IP exists later in the array, Runestone MAY move one occurrence to index `0`, but MUST record the original index as `moved`.
### DMN-008 — If Target IP is already at index `0`, Runestone MUST make no DNS-array mutation and MUST record the operation as `unchanged`.
### DMN-009 — Disable MUST remove only an `inserted` occurrence owned by Runestone.
### DMN-010 — Disable MUST restore only a `moved` occurrence's original position when ownership is not in conflict.
### DMN-011 — Disable MUST NOT restore an entire saved daemon file or overwrite unrelated user edits.
### DMN-012 — When Target IP changes, Runestone MUST inverse the previous owned operation and prepend the new Target IP in one transaction.
### DMN-013 — Missing or corrupt ownership state MUST cause a fail-safe error; Runestone MUST NOT guess which DNS entry to remove.
### DMN-014 — A `dns` key created by Runestone MUST be removed only when no other daemon configuration requires that key.
### DMN-015 — Daemon JSON writes MUST be atomic and MUST validate the resulting JSON before restart.
### DMN-016 — Concurrent DNS operations MUST be serialized per Runestone installation.

### 5.5 Upstream DNS

### UP-001 — Runestone MUST NOT add, remove, or reorder user fallback DNS entries.
### UP-002 — Existing usable daemon DNS entries MUST be used as dnsmasq upstreams.
### UP-003 — If no usable daemon DNS entries exist, Runestone MUST capture Docker's effective pre-change resolver without changing daemon DNS.
### UP-004 — Loopback resolvers MUST NOT be written as dnsmasq upstreams.
### UP-005 — If no usable upstream resolver can be determined, enable MUST abort before daemon mutation.
### UP-006 — dnsmasq MUST NOT forward queries back to its own Target IP.

### 5.6 Lifecycle

### LIFE-001 — `runestone up` MUST start and validate the DNS service before the main service when DNS is enabled.
### LIFE-002 — `runestone up` MUST reconcile a changed Target IP.
### LIFE-003 — `runestone stop` MUST stop only the main Runestone service when DNS is enabled.
### LIFE-004 — `runestone down` MUST disable DNS ownership before removing the DNS service or network.
### LIFE-005 — If DNS disablement or daemon restart fails, `runestone down` MUST abort before destructive teardown.
### LIFE-006 — DNS disable MUST stop/remove the DNS service and generated UI route only after daemon ownership removal succeeds.
### LIFE-007 — Certificate create/remove operations MUST refresh managed mappings when DNS is enabled.

### 5.7 Platform and safety

### PLAT-001 — Windows and macOS Docker Desktop MUST use the active Docker Desktop daemon configuration and restart mechanism.
### PLAT-002 — Linux rootful Docker Engine MUST support `/etc/docker/daemon.json` and the host Docker service restart mechanism.
### PLAT-003 — WSL2 MUST modify the Windows Docker Desktop daemon configuration when the active Docker endpoint is Docker Desktop.
### PLAT-004 — Remote contexts, Windows container mode, and unsupported rootless port-53 environments MUST fail before mutation.
### PLAT-005 — A TCP or UDP listener already occupying port 53 MUST prevent enablement before daemon mutation.
### PLAT-006 — Docker daemon/Desktop restart MUST wait until Docker is responsive before reporting success.
### SAFE-001 — Daemon file permissions MUST be preserved where the platform permits.
### SAFE-002 — A failed restart or DNS verification MUST roll back the Runestone daemon mutation.
### SAFE-003 — If rollback fails, ownership state MUST remain pending and the CLI MUST show the exact daemon path and manual recovery instruction.
### SAFE-004 — Existing user-authored Compose and dynamic configuration files MUST NOT be overwritten except for Runestone-managed DNS files.

## 6. Persistent state

### 6.1 Environment values

```dotenv
DNS_ENABLE=false
DNS_HOST_IP=
```

`DNS_HOST_IP` is Runestone-managed and identifies both the host binding and the DNS response address.

### 6.2 Ownership state

The tool state contains a versioned DNS record equivalent to:

```json
{
  "dns": {
    "schemaVersion": 1,
    "contextName": "local",
    "daemonPath": "/etc/docker/daemon.json",
    "targetIp": "172.17.0.1",
    "operation": "inserted",
    "originalIndex": null,
    "dnsKeyExisted": false,
    "daemonFileExisted": true,
    "phase": "applied",
    "upstreamResolvers": ["192.168.1.1"]
  }
}
```

Valid operation values are `inserted`, `moved`, and `unchanged`. Only `inserted` and `moved` represent removable Runestone ownership.

The transaction phase is `prepared` before daemon mutation and becomes `applied` only after daemon restart and DNS verification succeed.

### 6.3 Managed project files

```text
configuration/dns/managed.conf
configuration/dns/custom.conf
configuration/dns/upstream-resolv.conf
configuration/dns/dns-ui.yml
```

- `managed.conf` and `dns-ui.yml` are Runestone-owned.
- `custom.conf` is user-editable through Webproc.
- `upstream-resolv.conf` is Runestone-generated and does not contain Target IP.

## 7. Operation flows

### 7.1 Enable

1. Verify setup, local Docker context, supported platform, port 53 TCP/UDP availability, and valid daemon JSON.
2. Resolve Target IP from Docker using `host.docker.internal`.
3. Determine upstream resolvers without modifying user daemon DNS settings.
4. Persist `DNS_ENABLE=true`, `DNS_HOST_IP`, managed DNS files, and a `prepared` ownership record.
5. Start the DNS service and verify dnsmasq is listening on TCP and UDP 53.
6. Atomically prepend Target IP to daemon `dns` and persist the ownership operation.
7. After confirmation, restart Docker daemon/Desktop and wait for Docker readiness.
8. Verify that a newly created container resolves a Runestone certificate domain to Target IP.
9. Mark ownership `applied` and report the UI URL.

The failure boundary for this flow is defined by `CLI-006`, `DMN-015`, and `SAFE-002`.

### 7.2 Disable

1. Confirm the recorded Docker context and daemon path still match the active environment.
2. Read the current daemon JSON and apply only the inverse of the recorded owned operation.
3. Atomically write and validate the result.
4. After confirmation, restart Docker daemon/Desktop and wait for readiness.
5. Verify that the owned entry is no longer active.
6. Set `DNS_ENABLE=false`, stop/remove the DNS service, remove the generated UI route, and clear ownership state.

The absent-or-ambiguous ownership case is defined by `DMN-013` and `LIFE-005`.

### 7.3 Target IP rotation

When the resolved Target IP differs from recorded state, `up` or `dns enable` applies the `DMN-012` rotation behavior.

## 8. Failure semantics

| Condition | Required result | Retryability |
|---|---|---|
| Port 53 TCP/UDP occupied | Same prompt displays the error; no daemon mutation | After port is freed |
| No IPv4 Target IP | Abort before mutation | After Docker environment is fixed |
| Invalid daemon JSON | Abort before write | Yes |
| Remote context | Reject operation | After switching context |
| Missing ownership state on disable/down | Fail safe and show recovery path | After manual recovery |
| User changed DNS array | Preserve unrelated changes and report ownership conflict | Yes |
| Docker restart failure | Roll back daemon mutation | Yes |
| DNS verification failure | Roll back daemon mutation and stop newly started DNS service | Yes |
| Setup cancellation | No configuration or daemon changes | Yes |

## 9. Compatibility and migration

- Existing installations without `DNS_ENABLE` remain DNS-disabled.
- Existing daemon DNS arrays remain byte-semantically equivalent except for the owned Runestone operation.
- Existing user-authored Compose and dynamic configuration files are preserved.
- The DNS-capable image is published before the CLI presents DNS as available.
- The default image tag is updated in the same release as the DNS-capable image, while users can still override image and tag settings.

### CLI and prompts

- Test actual `runestone setup` entrypoint for DNS prompt, warning text, review output, same-prompt validation retry, cancellation, and default-disabled behavior.
- Test `runestone dns enable|disable|status` success, failure, exit codes, and read-only status behavior.

### Daemon ownership

- Enable with no daemon file.
- Enable with unrelated daemon keys and existing DNS entries.
- Enable when Target IP is already first.
- Enable when Target IP exists later and verify original position restoration.
- Disable after unrelated user edits and verify only Runestone's owned operation is inversed.
- Rotate Target IP and verify old ownership is removed before new ownership is added.
- Test duplicate IPs, malformed JSON, missing state, context mismatch, and rollback failure.

### Runtime and Compose

- Render disabled and enabled Compose files.
- Verify independent DNS service profile.
- Verify `53/tcp` and `53/udp` publication bound to Target IP.
- Verify port 8080 is not host-published.
- Verify managed certificate mappings, root CA exclusion, invalid filename handling, and custom rule persistence.
- Verify DNS UI route targets `dns:8080`.

### Lifecycle

- Verify `up` starts DNS before the main service.
- Verify `stop` leaves DNS service running.
- Verify `down` disables ownership before teardown.
- Verify certificate changes refresh DNS mappings.

### Platform matrix

- Windows Docker Desktop.
- macOS Docker Desktop.
- Linux rootful Docker Engine.
- Linux Docker Desktop where supported by the active Docker endpoint.
- WSL2 using the Windows Docker Desktop daemon file.
- Negative tests for remote contexts, Windows containers, rootless port-53 restrictions, and occupied TCP/UDP 53.

### Live acceptance

With DNS enabled, create a temporary container after daemon restart and verify:

1. Its resolver configuration contains Target IP as the first daemon-provided DNS server.
2. `traefik.<HOST_DOMAIN>` resolves to Target IP.
3. A certificate-derived subdomain resolves to Target IP.
4. Disabling DNS removes only Runestone's owned daemon change.
